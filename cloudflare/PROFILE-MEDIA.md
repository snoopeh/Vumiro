# Private finished-cover backup (optional, disabled)

The account Worker includes this source feature, but its optional bucket is not
provisioned and the live `profileMediaEnabled` flag remains false. The 1.22.2
service rollout did not enable media storage. Existing legacy account sync
works without the binding and without migration 0007. To enable later, an explicitly
authorized operator must apply `migrations/0007_profile_media.sql` to ACCOUNT_DB and
bind a private R2 bucket as `PROFILE_MEDIA` on the account Worker. Do not enable a
public bucket URL, custom domain, or anonymous read access. No fake bucket names or
IDs are included in Wrangler configuration. Existing account prefix routing and
scheduled `runAccountMaintenance` already cover these endpoints.

## Client contract

Send the usual account JWT, registered device ID and token, plus
`X-Vumiro-Profile-Cards: 1` and `X-Vumiro-Profile-Media: 1`. Config includes
`profileMediaEnabled`. An absent binding returns 503 with
`code: profile_media_unavailable` for media operations; ordinary thumbnail sync
continues. The original source image and crop-source bytes never belong in this
protocol. Upload only the client-rendered finished cover.

POST `/api/v1/account/cover` accepts raw PNG, JPEG or WebP (1 MiB maximum,
3840 x 1280 maximum, exactly 3:1 aspect ratio), a matching Content-Type, and `X-Vumiro-Cover-Manifest` JSON:

    {version:1, revision:<lowercase UUID v4>, digest:<base64url SHA-256 of bytes>,
     mime:<image/png|image/jpeg|image/webp>, width, height, bytes,
     thumbnailDigest:<base64url SHA-256 of UTF-8 profile.banner data-URL string>}

The response is `{cover: manifest}` (201, or 200 for an identical already-ready
revision). Object keys are independently generated by the server, never accepted
from the client. Manifest ordering does not matter. Digest values are canonical
unpadded base64url. Content-Encoding and unknown manifest fields are rejected.

After successful staging, PUT the normal account snapshot with `profile.cover`
set to that returned manifest and the normal `expectedRevision`. CAS commits the
pointer only if the same account owns an identical ready revision and the banner
matches its digest. A stale snapshot returns 409. A bad reference returns 400.
A capable client omits cover to remove it. Older clients do not receive cover on
GET, and an old write retains it only while the effective saved banner is unchanged.
Exports retain the manifest. To export cover bytes too, the updated client must
fetch the current binary endpoint while authenticated and include those bytes in
its export; the JSON export deliberately never contains binary/base64 media.

GET `/api/v1/account/cover/{revision}` returns only the current committed cover to
its owner and active registered device. Staged/obsolete/other-account revisions
return 404. Binary responses are private/no-store, nosniff, attachment, sandboxed;
there are no permanent public links or bearer tokens in a URL. New devices restore
the manifest and explicitly fetch these authenticated bytes, verifying the digest.

## Storage, deletion and validation

The transactional reservation cap is four objects/account total (one current plus
up to three staged revisions), each at most 1 MiB. Unreferenced ready revisions
expire after one hour; replaced current revisions are eligible immediately. Cleanup atomically marks them deleting before touching R2;
CAS can never publish a deleting row. Failed writes/deletes retain metadata for
maintenance retry. Writing rows orphaned by a crashed request expire after one
hour, to bound reservations left by failed requests. Expired writing rows are marked
deleting and removed in the following pass. A persisted-cursor bucket sweep also
removes untracked objects older than one hour, including late writes after stale
reservation cleanup; this reconciles the non-transactional R2/D1 crash boundary. Do not configure an
R2 lifecycle that expires current objects independently of D1.

Account deletion first blocks all account operations and removes the snapshot and
devices. It does not mark deletion complete or delete the identity until R2 cleanup
succeeds and all media rows, including in-flight uploads, are gone. Losing the R2
binding while media rows exist intentionally keeps deletion pending. Restore that
binding to finish cleanup. Maintenance retries failed cleanup; request-time staging
also sweeps that account's expired objects.

Raster verification validates MIME signatures, framing, dimensions, PNG chunk CRCs
and zlib envelope, and rejects animation/metadata/concatenated containers. All three
formats use structural-only storage validation, not full entropy/pixel decoding.
PNG no longer inflates pixel data in JavaScript: a 19 KB input can expand to nearly
20 MB, making full inflation unsuitable for the Worker hot path. Malformed entropy,
Adler32, or scanline data within a structurally valid PNG is not rejected server-side.
JPEG/WebP have the same decoder trust boundary. Clients must decode/re-encode before
upload and decode/verify dimensions before displaying restored data. The client must render/re-encode, not send original files. Full server-side
transcoding would require a separately reviewed image service/runtime dependency.

Run `node --test accounts.test.js account-routes.test.js profile-media-raster.test.js`
from cloudflare for focused checks. Tests use SQLite and in-memory R2 only.

## Bounded maintenance and performance evidence

A shared explicit media budget reserves at most 20 D1/R2 operations per account
maintenance invocation (remaining/used counters). Claims/deletions and orphan listing
are limited to four rows/objects per pass. Cursor progress is retained across
invocations; a page interrupted by budget exhaustion retains its cursor for retry.
Account maintenance processes at most two pending identity deletions per invocation,
leaving headroom for authentication, provider calls and ordinary housekeeping under
free-tier request/query constraints. This is a bounded source design, not a claim
that the whole Worker deployment meets every free-tier limit. Other scheduled work,
traffic volume, R2 billing/activation rules, D1 CPU and Cloudflare limits still need
verification before any deployment or free-cost promise.

Local Windows Node benchmark (2026-11-10), inspectRaster only, ten calls each:
- 3840 x 1280 RGBA flat PNG, 19,182 bytes: first 0.529 ms; subsequent 0.038-0.082 ms.
- Same dimensions, 979,799-byte PNG: 1.783-1.898 ms.
- Earlier full-inflation validator measured approximately 76-93 ms on the same
  dimensions; replacement avoids work proportional to decoded pixel count.

These are local wall-clock measurements, not Cloudflare CPU measurements; JWT,
digest, request parsing, database and R2 work are excluded. Actual Cloudflare
performance, cold-start behavior and free-plan compatibility remain unverified.
No media bucket, paid-plan choice or media infrastructure changes were made.
